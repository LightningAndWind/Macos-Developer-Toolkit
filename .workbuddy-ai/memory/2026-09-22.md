## 修复：SSH 连接崩溃（EventLoop.preconditionInEventLoop）

用户报的崩溃栈：`EventLoop.preconditionInEventLoop` @ NIOCore/EventLoop.swift:1437 → 即 `assertInEventLoop` 失败（`debugOnly` 包裹，**仅 Debug 崩**，Release 下是静默数据竞争）。

**根因**：`Tools/SSH/Logic/SSHClient.swift` 的 `openShell(on:cols:rows:output:onClose:)` 在主线程（MainActor 上下文）直接调了
`sshHandler.createChannel(...)`。两个独立违规：
1. `NIOSSHHandler.createChannel` 的文档注释写明 "This function is **not** thread-safe: it may only be called from on the channel" —— 它直接改 `pendingChannelInitializations`（Deque）。
2. 其 `channelInitializer` 里用了 `eventLoop.makeCompletedFuture`，而 NIOCore 的实现是 `Result(catching: body)` —— **在调用线程上就地执行闭包**。于是 `pipeline.syncOperations.addHandler` 跑在非事件循环线程上，撞 `ChannelPipeline` 内部的 `assertInEventLoop`。

**修法**：改成用 future 回调承载，`conn.pipeline.handler(type: NIOSSHHandler.self).flatMap { sshHandler in ... }`。
依据 `EventLoopFuture._internalWhenComplete`：`inEventLoop ? 就地执行 : eventLoop.execute { … }` —— future 回调**保证**在所属事件循环上跑。
顺带好处：`sshHandler` 是回调入参而非捕获值，不会新增 non-Sendable 捕获告警（对比 `eventLoop.execute {}` 的写法会产生 2 个新告警）。

**排查手法**（下次遇到 NIO 断言崩溃照这个走）：
1. 崩在 `preconditionInEventLoop` → 是 `assertInEventLoop` 失败（Debug-only），别去查数据竞争以外的东西。
2. `grep -rn "assertInEventLoop" <swift-nio>/Sources/NIOCore` 列出所有断言点：`ChannelPipeline.channel`（内部属性，`syncOperations.*` 会碰）、`SynchronousOperations.fireChannel*`、`AsyncChannel` 等。
3. 再 grep 依赖库（如 swift-nio-ssh）的文档注释，常直接写着线程要求。
4. 反例要警惕：`makeCompletedFuture` / `makeSucceededFuture` 的闭包是**就地执行**的，不是 hop。

## 修复：SSH 连接的生命周期（泄漏 + 重连误判）

在同一个文件里继续排查 `SSHClient` 的引用关系，又发现两个真问题：

**① SSHClient 永不析构（线程 + 连接泄漏）**
`watchClose()` 原本写成 `Task { [weak self] in guard let self else { return }; await self.closeSignal.wait() }`。
`guard let self` 会在**整个挂起期间强持有** SSHClient。而关标签走的是 `TabManager.close`，它只把 Tab 从数组移除、
**没有任何断开钩子**（`disconnect()` 只被 banner 的「断开」按钮调用）。于是 Tab / SSHTool 都释放了、SSHClient 却因这个
永久挂起的 Task 永不 deinit —— 它的 `MultiThreadedEventLoopGroup` 线程与 TCP 连接一起泄漏，
`deinit` 里那句 `group.syncShutdownGracefully()` 从来没执行过。
修法：`watchClose(_ signal: AsyncSignal)`，只捕获 signal（Sendable），不跨挂起点强持有 self。

**② 重连后立刻显示「已断开」**
`AsyncSignal.fired` 是单向闩锁，而整条连接共用同一个实例；`disconnect()` → `teardownChannels()` → `channelInactive`
已经把它触发过一次。重连成功后再 `watchClose()`，`wait()` 立即返回 → `guard case .connected` 通过 → 立刻置 `.disconnected`。
修法：每次 `connect()` 新建 signal，`onClose` 直接捕获本次的 signal（顺带省掉一次 hop 回主线程）。

**③ deinit 收尾（新增的坑）**
`BaseSocketChannel.deinit` 会断言 `canBeDestroyed`（通道必须已 closed）——**带着未关闭的通道析构会在 Debug 下崩在
"leak of open Channel"**。所以 deinit 必须「先关通道 → 再 `syncShutdownGracefully()`」（后者会等事件循环把 close 处理完）。
但 `SSHClient` 是 `@Observable` + `@MainActor`：
- deinit 是 nonisolated，读不到 MainActor 隔离的可变属性（`group` 是 Sendable 的 `let` 才能读）；
- 更关键的是 `@Observable` 会把存储属性改写成「计算属性 + `_xxx` 存储」，在 deinit 里读它会触发 Observation 的
  `access(keyPath:)`，对象正在析构 —— **不安全**；宏也不允许给这些属性加 `nonisolated`。
最终做法：把 `connectionChannel` / `shellChannel` / `closeSignal` 连同 teardown 逻辑一起挪进
`private nonisolated final class NIOResources: @unchecked Sendable`，`SSHClient` 只持有 `private let nio = NIOResources()`。
`let` 不会被 `@Observable` 追踪，deinit 里 `nio.teardown(group: group)` 就是普通存储属性访问。

## 修复：补上「关标签」生命周期契约（根治上面那类泄漏）

**根因**：`TabManager.close(tabID:)` 只把 Tab 从数组移除，**从不通知工具**。而工具持有的网络连接、
事件循环线程、子进程都不会因为对象被释放就立刻回收 —— 上面 ① 的泄漏、以及下面这个引用环，根都在这里。

**引用环（SSHTool ⇄ 连接 Task）**：`requestTrust` 把 continuation 存进 `pendingTrust`（在 SSHTool 上），
而发起连接的 `Task { await client.connect(…) }` 又强持有 SSHTool。
用户在 TOFU 信任提示上**直接关标签**时，没有任何代码调用 `resolveTrust` → 两者永远互相持有 →
SSHTool + SSHClient（含事件循环线程与 socket）一并泄漏。这个环靠 `deinit` 也救不回来（有环就不会 deinit）。

**做法**：给 `DevkitTool` 加可选生命周期方法（默认空实现），`TabManager.close` 在移除前调用：

```swift
// ToolProtocol.swift
@MainActor func teardownOnTabClose()      // 默认 {}；用于释放连接/子进程/句柄，并放行挂起任务
// TabManager.close(tabID:)
closing.toolInstance?.teardownOnTabClose()

// SSHTool
func teardownOnTabClose() {
    resolveTrust(trusted: false)   // 先让挂起的连接任务退出
    clearSession()                 // 再释放连接资源
}
```

**注意**：`TabManager` 没有显式写 `@MainActor`，但工程设了 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
（`SWIFT_VERSION = 5.0`），所以它本身就是 MainActor 隔离的，可以直接同步调 `@MainActor` 方法。
以后判断「能不能直接调 MainActor 方法」先看这个设置，别被「类声明上没写 @MainActor」误导。

**顺带排查结果**（同类风险全项目扫过，都是干净的，不用改）：
- `SSHTerminalContainer.Coordinator`：`Task { [weak self, weak view] in … for await … }` 只捕获 stream，
  且 `dismantleNSView` 里 `cancel()`；`AsyncStream` 迭代器响应取消。✓
- `LocalTerminalContainer`：进程交给 SwiftTerm 的 `LocalProcessTerminalView` 自行管理。✓
- `AppState.scheduleSessionSave` 的防抖 Task：`[weak self]` + 有界 `sleep`，正常结束。✓
- `HTTPTool` / `JSONTool`：无外部资源，无需实现 `teardownOnTabClose`。

## 补完设置面板引入的一条可达缺陷（早前标记、被 SSH 崩溃打断）

**症状**：在设置面板删掉一条已保存请求后，若标签仍绑着它，用户按 ⌘S **毫无反应**（不报错、不弹框）。

**原因**：`HTTPTool.saveViaShell()` 原本是
`guard let id = savedRequestID, let existing = HTTPCollectionStore.load(id: id) else { return }` ——
记录被删后 `load` 返回 nil，直接静默 return。而且只要 `savedRequestID` 还在，下次 ⌘S 仍走同一条死路。
（这条路径在我做设置面板之前是**不可达**的：那时没有任何入口能删已保存请求。）

**修法**：
1. `saveViaShell()` 拆开两个 guard：记录不存在时调 `detachSavedRecord()` 再返回 ——
   `isSaved` 转为 false，Shell 下次 ⌘S 改走「另存为」弹框，自愈。
2. `SettingsView.deleteSavedRequest` 里解绑后补 `appState.scheduleSessionSave()`：
   解绑改变了 `savedRequestID` / `lastSavedRequest` 这两个可持久化字段，
   不落盘的话强杀或开发重编译后，会话快照里还留着指向已删记录的 ID。

**顺带**：设置面板「历史记录」的计数徽标原来固定显示 `historyTotal`，搜索时不跟列表走，
与「已保存请求」不一致。抽出 `isSearchingHTTP` / `historyBadgeCount`：
搜索时显示命中数，不搜索时才显示真实总数（摘要只取最近 300 条，不能用 `historyRecords.count` 冒充总数）；
「仅显示最近 N 条（共 M 条）」提示也只在非搜索态出现。

## 收尾加固：两处不严谨 + 自检扩到 26 项

**① `AppState.deleteSavedHTTPRequest`：删除失败时不该解绑**
原来无条件解绑绑定该 id 的标签。但 `HTTPCollectionStore.deleteRequest` 在库未打开时是**静默 return**，

## 修复：重连后终端永远空白（AsyncStream.finish 是终态）

**症状**：SSH 会话点「断开」→「重新连接」后，**终端再也不显示任何输出**（连接其实是好的）；
「换个目标」后同理。

**根因**：`SSHClient.disconnect()` 里调了 `outputContinuation.finish()`。
`AsyncStream.Continuation.finish()` 是**终态** —— 之后所有 `yield` 都被静默丢弃。
而消费端 `SSHTerminalContainer.Coordinator` 只在视图首次出现时订阅一次
（`startConsumingIfNeeded` 有 `started` 门闩），不会重新订阅。
于是新会话的 `onOutput`（`self?.outputContinuation.yield(bytes)`）全部丢进了已终止的流。

**修法**：从 `disconnect()` 里删掉 `finish()`。输出流的生命周期应跟随 **client** 而非单次连接：
- 消费任务靠视图 `dismantleNSView` → `stopConsuming()` → `cancel()` 结束（`for await` 响应取消）；
- client 释放时 continuation 一起释放，流自然终止，无需显式 finish。

**自检覆盖**（第 28 项）：订阅 `client.incoming`，`disconnect()` 后断言消费任务**没有**结束。
**并验证了这条检查有牙齿**：临时把 `finish()` 加回去重跑，精确报
`FAIL disconnect 不应终止输出流`；移除后恢复 PASS。

**教训**：这和之前的 `AsyncSignal.fired` 是同一类坑 —— **「一次性/终态」语义的对象被跨多轮生命周期复用**。
审查时凡是看到 `finish()` / `fired = true` / `isClosed = true` 这类单向状态，都要问一句：
「第二次用的时候它还是活的吗？」另外，把 `finish()` 放在 per-connection 的 teardown 里是典型的
「资源生命周期挂错了层级」—— 流的归属者是 client，不是 connection。

## 修复：HTTP 工具会命中响应缓存

`HTTPClient.send` 用的是 `URLSession.shared`（默认 `.useProtocolCachePolicy` + 磁盘缓存）。
对**调试工具**这是错误行为：重复发同一个 GET 可能直接命中缓存返回旧响应，
状态码 / 耗时 / 响应体全对不上真实情况，而现象是「时好时坏」，很难联想到缓存。

改为共享的私有 `URLSession`，只关缓存、不动 cookie：

```swift
private static let session: URLSession = {
    let config = URLSessionConfiguration.default        // 保留共享 cookie 存储
    config.requestCachePolicy = .reloadIgnoringLocalCacheData
    config.urlCache = nil
    return URLSession(configuration: config)
}()
```

**刻意不用 `.ephemeral`**：那会连 cookie 一起隔离掉，依赖会话 cookie 的接口（登录后再调）就废了。
顺带把 `URLSession` 提成 `static let`，避免每次发送都新建会话。

**未加自检**：这属于配置项，写断言只会是把配置再念一遍（恒过的断言没有价值）。
也**没做行为级验证** —— 需要真实网络请求，本环境不可靠。改动本身 3 行、可直接审视、可一行回滚。

### ⚠️ 本轮最大的坑：`nonisolated` 在本工程**不换执行器**

工程开了 `SWIFT_APPROACHABLE_CONCURRENCY = YES`，Swift 6.2 下它启用 `NonisolatedNonsendingByDefault`
（SE-0461）→ **`nonisolated` async 函数沿用调用方执行器**。`send` 在主 actor 上，
所以只标 `nonisolated` 的 `receive` **仍跑在主 actor**：循环每取一个字节 hop 一次主 actor（约 5~6 µs），
10 MB 直接撞满 30s 请求超时。

对照实验（同一循环体、同一夹具、同一编译设置）：

| 写法 | 3 MB 耗时 |
| --- | --- |
| `nonisolated`（从主 actor 调用） | 17.5s |
| `nonisolated` + `Task.detached` | 0.14s |
| `@concurrent` | 0.14s |

**修法：`@concurrent`**（一个属性，不必改调用方）。修完自检总耗时从 30s+ 降到 1.96s。

两个误导点，都记进 skill 了：
1. **独立脚本复刻同样代码是快的** —— 因为 `swiftc` 默认没开那个 upcoming feature。
   复刻必须带 `-default-isolation MainActor -enable-upcoming-feature NonisolatedNonsendingByDefault`。
2. **现象像服务端问题**：小响应正常、大响应报 `The request timed out`。
   判断口诀：耗时随数据量线性放大且远慢于预期 → 先怀疑每元素 hop，别查网络。

## 第 4 轮：缺陷 #11（本地终端子进程泄漏）+ 缺陷 #12（旧历史记录解码静默消失）

### 缺陷 #11：`LocalTerminalContainer` 缺收尾钩子
- 根因：`makeNSView` 里 `startProcess` 启动 shell，但无 `dismantleNSView`；SwiftTerm `LocalProcess.deinit`
  只取消监视器、**不杀 shell 不关 PTY fd**；`SSHTool.clearSession()` 对本地会话是空操作
  → 每次关本地终端标签留一个孤儿 shell + 泄漏的 PTY master fd。
- 修复：`dismantleNSView` 里调 `nsView.terminate()`（关 DispatchIO → kill SIGTERM → childStopped，幂等），
  与 `SSHTerminalContainer` 同模式。
- 关键语义：`terminate()` 会**取消**本该负责 `waitpid` 回收的监视器 → 子进程死后短暂 zombie；
  自检判定「已结束」必须用 `waitpid(WNOHANG)`（>0=回收了僵尸；-1/ECHILD=监视器已回收），
  不能只看 `kill(pid,0)`（僵尸照样返回 0）。
- 自检新增 `checkLocalTerminalDismantleKillsShell`：夹具用 `/bin/sleep 300`（快、SIGTERM 即退、无 zshrc 副作用），
  两段式断言（先证 pid>0 且存活，再证 dismantle 后进程结束 + `childfd == -1`）。
- 牙齿验证：回退 `terminate()` → FAIL（pid 5s 后仍存活 + childfd=14）→ 恢复 → PASS。✓

### 缺陷 #12：`HTTPResponseSnapshot.isBodyTruncated` 破坏旧记录解码（升级兼容回归）
- 根因：上轮给 `HTTPResponseSnapshot` 加非可选 `isBodyTruncated`，Codable 合成解码走 `decode(_:)`，
  旧 JSON 无此键 → `keyNotFound`；`HTTPHistoryStore.fetch` 是 `try?` 吞错
  → **升级后所有旧历史记录从列表静默消失**（库里还在，UI 看不见）。
- 修复：自定义 `init(from decoder:)`，该字段 `decodeIfPresent(...) ?? false`，其余字段严格解码；
  非可选语义保持，视图层零改动；`encode(to:)`/`CodingKeys` 仍合成，无需补写。
- 自检新增 `checkSnapshotDecodesLegacyJSON`：旧格式 JSON 字面量直接 decode 当前类型断言成功 + 新格式 true/false 原样读出。
- 牙齿验证：合成解码态 FAIL（`The data couldn't be read because it is missing.`）→ 修复态 PASS。✓
